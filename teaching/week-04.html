Prepare for a workshop

Use the student notebook for live coding and keep the instructor copy open separately. The notebook and project page are the presentation surfaces for this session. No new biological algorithm is required. The guided exercise supports students who need practice with basic syntax and notebook execution. The separate coding projects assume intermediate Python: students can write functions, work with lists and dictionaries, read files, debug errors, and use a plotting library.

  • Download both notebooks before class. Upload the student copy to Colab if its GitHub launch link is not yet available. Prepare a local Jupyter copy for your own fallback.
  • Run the notebook once, then make a clean teaching copy. Check that matplotlib can display a plot. A printed-results fallback is included; use the lesson’s saved preview if a student cannot draw locally.
  • Increase code font size for projection. Show one short cell and its output together. Say what you are about to type before typing it.
  • Ask pairs to alternate the person who types and the person who predicts. Each student should still save a personal notebook and write an explanation.
  • Use the examples as supplied initially. An open-ended real-data fetch or package installation would add work unrelated to today’s Python goals.

Week 4 is now the programming workshop and project introduction. DNA variation was the previous course-map placeholder. Its later placement remains a curriculum decision; this session does not compress variant calling into the coding exercise or assume an eleventh week.

Live-coding checkpoints and answers

Steps 1–2: separate text from names
dna = "ATGCGCAT" gives length 8. Appending A gives 9. dna[0] is A; dna[2:6] is GCGC; dna[0:4] is ATGC. Ask students to read a slice as “start here, stop before here.”
Step 3: show the whole fraction
Original: 2 G + 2 C out of 8 → 50%. Changed ATATGCAT: 1 G + 1 C out of 8 → 25%. Avoid hiding the calculation inside a function at this point.
Step 4: trace a loop
The three fragments all have length four. Adding print(fragment.count("G")) inside the loop adds counts 0, 2, 1. Outside the loop it prints only the final count, 1. Explain that indentation determines which instructions repeat.
Step 5: connect range to slices
The starts are 0,10,20,30,40,50. At start 10, slice 10:20 is GCGCGCGCGC. Change both step and width to 20 to cover all 60 bases in three windows. Changing only the step to 20 leaves gaps.
Step 6: build lists visibly
After the first iteration: starts [0], widths [10], percentages [0]. After the second: [0,10], [10,10], [0,100]. Completed percentages: [0,100,40,40,60,60]. Lists are reset above the loop every time the cell runs.
Step 7: calculate before interpreting the plot
Size 20 gives [50,40,60]. The first window combines ten A/T bases with ten G/C bases. Its 50% summary hides that sharp change. For unequal window sizes, an average across windows requires weights; the code instead calculates each window directly from its actual length.
Mini-browser: crop the view, preserve the annotation
A is [12,26), B is [38,54). In view 10:40, all of A and only B’s 38:40 portion appear. View 26:38 contains neither feature. A touching boundary is not an overlap under this convention. GC bins remain anchored to the original calculation.
Follow-up transfer
GGCCATATGC has six G/C bases out of ten → 60%. Its first four letters GGCC have four out of four → 100%. Dividing the latter count by ten would give an incorrect 40% for the slice.

When students need more support

Ask “Which cell did you run last, and what did you expect?” Start with the input and output, then inspect the highlighted line. Avoid taking over the keyboard. For a missing variable, rerun its definition; for stale output, rerun the dependency and plot; for indentation, draw a vertical line beside the loop body.

If many students cannot trace the Step 4 loop, use the first ten minutes after the break to repeat that trace. Supply Steps 5–6 unchanged and ask students to explain just the first window. Omit the optional renderer demonstration and reduce project pitches to one minute each to recover time. Preserve the break, project choice, and an opportunity for every student to make one successful edit.

Students who finish early can try size 7 and inspect the shorter final window, or test a viewport touching a feature boundary. They should explain the observation to a partner before adding an interface or a new library.

Presenting the project options

Show the two full research examples and two full coding examples. Give each three minutes: question, required work, final result, and one check. Then spend four minutes scanning the ten one-line alternatives. Students choose a single research or coding project; the alternatives are not additional tasks.

  1. Research — Sequencing mechanisms: “Compare how two physical signals become DNA letters, using evidence relevant to one sequencing task.”
  2. Research — Repeats and assembly: “Explain a documented ambiguity, then show which observation distinguishes two toy reconstructions.”
  3. Coding — Genome-region browser: “Load reference and annotation files, navigate a region, and show that both tracks use the same coordinates.”
  4. Coding — LLM question-answering: “Retrieve a few bioinformatics passages, generate an answer with source IDs, and measure whether the answer is supported.”

For the seven-minute worked check, spend three minutes on browser views 0:60, 10:40, and 26:38, then four minutes on the LLM example. P01 states that ATGCGCAT has four G/C bases out of eight: an answer of 50% citing P01 is supported. A nanopore-current number is unsupported unless a supplied passage reports it. Ask students to distinguish a valid source ID from a source that actually supports a claim.

The LLM is the component students build around and evaluate. Its brief is a coding assignment, with no separate literature-review requirement. Research options on LLM evaluation remain research assignments using published evidence, with no programming deliverable.

Do not require students who prefer research to choose coding. A research project needs a concrete question, traceable sources, and an original explanation; a coding project needs a working implementation and evidence about its behavior. The one-line ideas use the same final-submission requirements as their corresponding type.

Optional notebook appendix: the Smith–Waterman simulator lets students edit two sequences, a 4×4 substitution matrix, and a negative linear gap score. Run its loader and settings cells, then use the calculation cell or optional widgets. TTACGTAA / GGACGTCC gives ACGT / ACGT, score 8, with [2,6) intervals in both sequences. The fill slider and inspected-cell calculation expose the DP steps. Tied optima are resolved deterministically, so the output need not be unique. This appendix adds no required time to the class or homework.

Six weeks, approximately 24 hours, 30% of the final grade

Students complete one final project within six weeks, with an expected investment of about four hours per week, or 24 hours total per student. This includes source reading, coding or analysis, validation, writing, and preparing the final explanation. Students organize their own time. There are no weekly milestones, progress reports, or interim submissions. Announce the exact calendar deadline, submission location, and whether teams are permitted.

The student page contains the final requirements for research and coding projects.

  • Research: 4–6 pages excluding references, at least six relevant sources including two primary studies or technical reports, a comparison of evidence, and an original worked example or explanatory figure. Evaluate synthesis and the handling of uncertainty, not just a summary of sources.
  • Coding: an intermediate-Python tool or analysis with file input, functions, validation, automated checks, a documented example, reproducible output, and a 2–3-page explanation. The selected brief defines the required calculations and interface; a notebook is acceptable.

Research projects finish with an eight-minute presentation and questions; coding projects finish with an eight-minute demonstration and questions. Slides are optional. If teams are allowed, require individual contribution statements and ask each student to explain one result or decision. Optional extensions are not necessary for full marks.

Keep the required work within 24 hours

Limit each project to the stated dataset or case and one principal question. For the browser, one small reference region, a documented FASTA/BED subset, two main tracks, and local notebook controls are sufficient. For the LLM project, use one already accessible model, 10–15 short passages, and 12 questions (four for development and eight held out, including two unanswerable from the passages). Check model access before the student commits to the topic; avoid infrastructure setup or training that would consume the project budget. For research, one comparative question and six carefully read sources are sufficient. Additional file formats, deployment, large datasets, and broad literature surveys should remain outside the core.

Students can reuse course examples with attribution. A project needs substantive work beyond those examples: data handling, an investigation with meaningful comparisons, and evidence that the result is correct. Changing colors or rerunning the supplied toy alone is insufficient. For example, the repeat research project compares published evidence and uses a hand-worked reconstruction diagram; the exact-match coding project delivers a tested search tool. Students choose one of these distinct types.

Research validation means checking source claims and worked examples; it does not require software tests. For coding, use independent numerical checks and malformed-input or boundary cases. A larger interface does not compensate for an incorrect result.

After-class work and exit prompt

The 60–90-minute follow-up comprises notebook recovery (10–15), the new-string transfer task (25–35), and personal project-selection notes (25–40). Those planning minutes count toward the project’s 24-hour budget. There is no separate proposal to submit and no interim project deliverable. The full project is submitted at the end of the six-week period.

Exit prompt: “Show one cell you changed. Explain its input, the operation, and the output. Then name one project core you could complete within 24 hours and one check you would use.”
